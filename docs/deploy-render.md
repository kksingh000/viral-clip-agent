# Deploying on Render

`render.yaml` in the repository root is a Render Blueprint that provisions the
whole stack. This page covers what you have to decide before running it, and
the two ways Render differs from the local Docker Compose setup.

---

## Read this first

### 1. Object storage is required

Locally, the API and the workers share a Docker volume (`media-data`): the API
writes an upload, the worker reads it, the worker writes a clip, the API serves
it.

**A Render disk attaches to exactly one service.** There is no shared
filesystem between the API and the workers. With `STORAGE_PROVIDER=local` the
worker would be unable to read anything the API uploaded, analysis would fail
with "source media not found", and every clip download would 404.

So `STORAGE_PROVIDER=s3` is mandatory. Any S3-compatible bucket works:

| Provider | Notes |
|---|---|
| Cloudflare R2 | No egress fees — the best fit for serving video. Set `S3_ENDPOINT_URL`. |
| AWS S3 | Leave `S3_ENDPOINT_URL` blank. Watch egress cost. |
| Backblaze B2 | Cheap storage, S3-compatible endpoint. |

The bucket needs no public access: the app serves everything through presigned
URLs with a configurable TTL.

### 2. The free tier cannot run this

- **Background workers are not offered on the free tier**, and the whole
  pipeline runs in workers.
- **Free web services sleep** after inactivity. A sleeping API means the
  dashboard fails to load and any queued work stalls.
- **Free Postgres expires** after a limited period.

The blueprint therefore specifies paid instance types. See
[Costs](#costs-and-how-to-trim-them) for what that means and where to trim.

## Before you deploy

You need, at minimum:

1. **A Render account** with the GitHub repository connected.
2. **An S3-compatible bucket** plus an access key pair scoped to it.

Optional but recommended, and addable later:

3. **`ANTHROPIC_API_KEY`** (or `OPENAI_API_KEY`) — without it every agent runs
   its deterministic fallback. The pipeline works; the moment selection is far
   weaker, and `/health` reports `llm: degraded`.
4. **A transcription provider.** `openai` is the light option (hosted, no
   worker memory). `faster_whisper` runs on-box and needs the Standard worker.
   Without either, transcripts are structural only and moment detection
   refuses to run rather than reading placeholder text.
5. **`YOUTUBE_API_KEY`** — enables trend discovery. Metadata only.

## Deploy

1. In Render: **New → Blueprint**, select the repository, review the plan.
2. Render prompts for every variable marked `sync: false`. Fill in at least the
   five `S3_*` values. Leave provider keys blank to start in the honest
   no-credential mode.
3. Apply. First build takes a while — the worker image installs ffmpeg,
   OpenCV and the CTranslate2 wheels.

`SECRET_KEY` is generated by Render (`generateValue: true`) and shared with the
workers via `fromService`, so tokens signed by the API verify in the workers.
It never appears in the repository.

Database migrations run as the API's `preDeployCommand` (`alembic upgrade
head`), which completes before any new instance serves traffic.

## Verify

```bash
curl -s https://viralagent-api.onrender.com/health | jq
```

A correct deployment returns HTTP 200. Read `components`, not just `status` —
`degraded` is a legitimate state that tells you what is not configured:

| Component | `degraded` means |
|---|---|
| `llm` | `LLM_PROVIDER=mock`; agents are using deterministic fallbacks. |
| `transcription` | `TRANSCRIPTION_PROVIDER=mock`; transcripts are structural only. |
| `task_queue` | **Not expected on Render.** The worker cannot reach Redis — check `REDIS_URL`. |
| `database` | **Never acceptable.** Check the connection string and that the DB is up. |

Then open the dashboard, register an account, and run a video through. The
banner across the top restates any degraded providers.

## Costs, and how to trim them

The blueprint's defaults, at time of writing:

| Service | Plan | Why |
|---|---|---|
| `viralagent-api` | Starter | Must stay awake; it is a thin API. |
| `viralagent-worker` | **Standard (2 GB)** | ffmpeg is memory-hungry; whisper adds ~1 GB. |
| `viralagent-beat` | Starter | Tiny — it only emits scheduled tasks. |
| `viralagent-web` | Starter | Static-ish Next.js server. |
| `viralagent-redis` | Starter | Broker; `noeviction` so jobs are never dropped. |
| `viralagent-db` | basic-256mb | Postgres 16. |

Ways to reduce it:

- **Drop the worker to Starter** if you use hosted transcription
  (`TRANSCRIPTION_PROVIDER=openai`). Whisper is what needs the 2 GB; ffmpeg
  alone fits in less. Long or high-resolution sources may still fail.
- **Drop `viralagent-beat`** if you do not use trend discovery or analytics
  sync. It only schedules metric refresh, analytics sync and stale-job
  reaping. Without it, nothing periodic runs — a killed worker's job stays
  `PROCESSING` until you cancel it by hand.
- **Suspend the worker** between batches. Jobs queue in Redis and drain when
  it resumes.

## Scaling

- **Workers scale horizontally.** Raise the instance count, keep per-worker
  `--concurrency` low (2–4) — ffmpeg is already multi-threaded, so stacking
  concurrent renders on shared vCPU makes each one slower without raising
  throughput.
- **Split the queues** when rendering dominates: run one service on
  `-Q render` and a smaller one on `-Q analysis,discovery,publishing`, so a
  long render never starves a quick analysis. Override `dockerCommand` to set
  `-Q`.
- **`viralagent-beat` must stay at one instance.** Two schedulers emit every
  periodic task twice.
- **The API is stateless** and scales freely. Rate limiting is shared across
  instances through Redis; if Redis is unreachable each instance falls back to
  counting on its own, so the effective limit multiplies by the instance
  count.

## Operational notes

**Render's filesystem is ephemeral.** `WORKDIR` (`/data/work`) holds ffmpeg
scratch — extracted audio, caption frames, intermediate renders — and is meant
to be disposable. It is also a cache: a deploy clears it, so the next analysis
re-extracts audio and re-transcribes rather than reusing what was there. That
costs time and, with a hosted transcription provider, money. Nothing is lost.

**Cold builds are slow.** The worker image installs ffmpeg, OpenCV and
CTranslate2. Render caches Docker layers between deploys, so only changed
layers rebuild — keep `requirements*.txt` edits separate from application
changes to preserve the cache.

**Postgres backups.** `viralagent-db` holds everything that cannot be
regenerated: rights records, approvals, analytics and score calibration
history. Render takes daily backups on paid plans; check the retention matches
what you need. The bucket holds source uploads and rendered clips — expensive
to lose, but reproducible from sources.

**pgvector.** Render's Postgres ships the extension. The Alembic environment
runs `CREATE EXTENSION IF NOT EXISTS vector` and continues without it if
permissions do not allow, since the `Vector` column type degrades to JSON. The
schema is ready for vector search; nothing currently issues one.

## Troubleshooting

**The dashboard loads but every request fails with a CORS error.**
`CORS_ORIGINS` on the API must contain the dashboard's exact origin. Render
supplies a bare hostname, which the API promotes to `https://` automatically —
but if you set it by hand, include the scheme and no trailing slash.

**"source media not found" on every analysis.** `STORAGE_PROVIDER` is still
`local`. The API and workers do not share a disk on Render; switch to `s3`.

**Clips render but downloads 404.** Same cause, or the S3 credentials differ
between the API and the worker. Both need the same bucket.

**The worker restarts during rendering.** Out of memory. Move to a larger
instance, or switch to hosted transcription so whisper is not resident.

**`/health` shows `task_queue: degraded`.** The API cannot reach Redis, so it
is running tasks in-process. Work will be slow and will not survive a restart.
Check `REDIS_URL` resolved from the `keyvalue` service.

**Jobs sit in `QUEUED` forever.** The worker is not running, is not connected
to the same Redis, or crashed on start. Check its logs — a missing
`SECRET_KEY` or `DATABASE_URL` fails fast and loudly.
